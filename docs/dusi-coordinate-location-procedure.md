# 都司坐标独立定位方式与操作流程

本文件用于都司、行都司和留守司首批点位的坐标定位、数据写入和批次验收。流程沿用 [CHGIS 坐标独立替换流程记录](chgis-replacement-procedure.md) 中验证过的“历史身份链 + 独立现代空间链 + 候选冻结 + 分批验收”方法，但本任务不是替换 CHGIS 坐标，也不以任何第三方历史 GIS 点位作为默认坐标来源。

本文件同时受以下规范约束：

- [历史数据规范](historical-data.md)：时间、来源、可信度、坐标参考系和许可要求。
- [数据分片与关系层模型](data-model.md)：稳定地点、军事单位、行政所在和军事关系分离。
- [军事图层与通用层级显示约定](military-display-and-hierarchy.md)：军事图层、着色、层级范围和独立选择链。
- [项目路线图](roadmap.md)：都司军事图层、军事浏览上下文和共址交互决策。

## 1. 适用范围与边界

### 1.1 首批范围

首批定位对象为：

- 都司；
- 行都司；
- 留守司。

后续卫、千户所、营堡、关隘和军镇沿用本流程，但应在军事关系和层级数据契约确定后另行分批，不与首批机构混成一张未经校勘的名录。

### 1.2 坐标的含义

本流程定位的是机构在目标时间切片中的治所、驻所或可审计的现代代理点，不是军事辖区边界，也不是明朝实际控制范围。坐标不得单独证明：

- 都司对某一行政区的管辖范围；
- 都司与府、州、县之间的行政隶属；
- 军事机构在战争期间的实际控制区域；
- 一个机构曾经设置后在 1600 年仍然存续。

机构类型、军事编制、所在行政区和实际控制关系分别记录。军事隶属不得通过修改行政单位的 `parentId` 表达，军事辖区不得由点位自动生成面状边界。

### 1.3 坐标参考系

发布坐标统一使用 WGS 84，经度在前、纬度在后。接口返回的原始经纬度必须保留足够精度；网页地图、搜索结果或格式化表格中的显示值不得直接写入正式数据。

## 2. 固定原则

每个军事点位必须形成两条彼此可审计的证据链：

1. **历史制度链**：证明机构名称、机构类型、1600 年有效性、军事关系及驻地描述。
2. **现代空间链**：从许可兼容且坐标参考系明确的现代地名源取得候选坐标，并记录来源记录、访问日期、原始数值和代理理由。

候选坐标必须在不查看、不复制任何 CHGIS 坐标的独立流程中取得并冻结。候选冻结后，才允许与既有行政点位或其他候选做距离、共址和同名冲突检查。距离接近不能证明候选正确，距离较远也不能自动证明候选错误。

如果史料明确说明军事机构与府、州、县治所同城或共用驻地，可以复用同一个稳定 `Place`；但必须先完成独立的历史对应判断，不能仅因两个坐标接近就合并地点或机构。共址复用地点，不等于合并军事单位和行政单位。

## 3. 点位清单与候选准备

### 3.1 先锁定机构身份

候选采集前，先建立首批清单，至少包含：

- 稳定 `militaryUnitId`；
- 历史名称、异体字和名称变体；
- 明确的机构类型：`dusi`、`xing-dusi` 或 `liushou-si`；
- 1600 年有效区间和时间精度；
- 历史来源、卷页或定位段落；
- 军事上级或同级关系的待核状态；
- 所在省级地区、可能共址的府州县和待核行政上下文；
- 是否已有可复用的稳定 `placeId`；
- 现有坐标、来源和审计信息是否属于本项目既有记录。

清单只锁定机构身份和历史问题，不先写入候选经纬度。机构名称不能直接作为稳定地点 ID，也不能把军事上级、驻地所在行政区和军事辖区混为一个父子关系。

### 3.2 历史身份链

优先使用覆盖目标年份的同期官方文献和点校可靠的历史地理资料，至少核对：

- 机构在 1600 年是否存在；
- 都司、行都司和留守司的机构类型是否准确；
- 机构名称和沿革是否存在同名、改名、迁移或裁并；
- 驻地是城内、府州县治所、卫城、旧城、堡寨还是仅能确定到区域；
- 军事关系和行政所在关系是否分别有来源支持。

历史来源只承担身份、时间、关系和对应判断，不直接承担现代 WGS 84 坐标。

## 4. 独立取得现代候选坐标

### 4.1 来源优先级

现代候选优先采用：

1. 允许项目发布场景使用的官方地名、遗址或地方公共数据；
2. Wikidata `P625`，通过官方 Action API 或 Query Service 读取实体和原始坐标；
3. GeoNames 等许可明确的现代地名数据；
4. Getty TGN 等补充交叉验证来源；
5. 其他来源明确、许可兼容且可审计的现代聚落或遗址资料。

高德、百度等在线地图的显示坐标不得作为默认正式来源。免费访问、搜索结果可见或公益用途不等于允许再分发。

### 4.2 Wikidata 读取规则

网页页面和搜索结果页只适合人工发现候选，不作为批量读取入口。批量或复核时使用：

- `wbsearchentities`：按历史名称、现代名称或行政关系发现候选实体；
- `wbgetentities`／`wbgetclaims`：读取实体标签、描述、`P625` 和原始数据值；
- 官方 Wikidata Query Service：按名称、类型、行政关系或空间范围筛选候选。

每次查询记录访问日期、接口、参数或查询语句、最终采用的 Q ID、原始经纬度和接口返回的 `precision`。`precision` 只作为来源属性审计，不等同于历史驻地精度。

### 4.3 候选对应规则

每个机构至少形成一个明确的“历史机构 → 现代候选”理由：

- 现代城市或县治代理：可定位到现代聚落，但历史驻所未解析，通常为 `approximate`；
- 现代遗址或城址代理：有较明确地点依据，但仍需说明是否为目标机构驻地，不能自动标记为 `exact`；
- 同城共址代理：历史来源明确记载同城或共用驻地时，可以复用行政 `Place`，并记录独立的军事共址关系；
- 区域代理：只能确定到较大区域时使用 `area_only` 或 `unknown`，不得凭现代城市连续性补造精确点；
- 同名候选、迁治、裁并或沿革无法排除时降低为 `low`，保留待复核事项。

候选锁定后，才允许与现有行政坐标进行距离检查。距离检查只能用于发现疑似同址、同名误配或迁治线索，不能把既有行政坐标反向写成军事坐标来源。

## 5. 候选表冻结

正式写入数据前，冻结一份候选表。每行至少包含：

| 字段 | 要求 |
|---|---|
| `militaryUnitId` | 稳定军事机构 ID |
| 历史名称／机构类型 | 都司、行都司或留守司及名称变体 |
| 1600 年状态 | 有效区间、时间精度、存续判断 |
| 历史对应理由 | 史料、驻地描述、沿革和同名消歧 |
| 现代代理 | 现代名称、聚落／城址／遗址类型 |
| 现代来源 | 来源 ID、Q ID 或其他官方记录编号 |
| 原始坐标 | WGS 84 经度、纬度和来源原值 |
| `precision` | 接口返回值，单独审计 |
| `locationAccuracy` | `exact`、`approximate`、`area_only`、`disputed` 或 `unknown` |
| `confidence` | `high`、`medium` 或 `low` |
| 行政上下文 | 所在省级地区、府州县或未知 |
| 共址关系 | 可复用的 `placeId` 和历史依据 |
| 待复核事项 | 迁治、同名、驻地范围和来源缺口 |
| 审核日期 | 候选冻结日期和复核人记录 |

候选表冻结后，替换候选必须逐条留下审计说明，不得用批量脚本静默覆盖整个区域。

## 6. 数据写入规则

### 6.1 单位、地点和关系分开保存

- 军事机构写入 `data/units/military/` 或明确的军事分片；
- 物理地点写入对应的 `data/places/` 分片；共址地点只保存一份稳定地点记录；
- 军事隶属、编制关系、行政所在和共址关系写入关系层，不以行政 `parentId` 代替；
- `data/project.json` 只能由 `data/manifest.json` 组装生成，不直接编辑或提交。

军事数据契约必须明确机构类型和关系类型，不能从中文名称后缀推断都司、行都司或留守司，也不能把“位于某府”误写成“隶属于某府”。

### 6.2 定位字段

每条地点记录至少保持：

- `locationAccuracy` 与实际证据一致；
- `locationMethod` 说明现代代理、独立来源、历史对应理由和未解析事项；
- `confidence` 与历史链、空间链和共址判断的最弱证据一致；
- 历史来源承担 `existence`、`name`、`time` 或军事关系主张；
- 现代空间来源承担 `location` 主张；
- `audit.reviewedOn` 和 `audit.revisionNote` 记录冻结、写入和后续修订原因。

建议的定位说明模板为：

```text
Modern military-seat proxy independently located from Wikidata Q..., guided by the Ming History military-institution description; exact historical command seat remains unresolved.
```

若复用已有行政地点，应明确写出军事机构与该地点的历史共址依据，不把行政地点的来源伪装成军事机构的独立历史定位来源。

## 7. 分批操作流程

每批按以下顺序执行：

1. 锁定机构清单、时间切片、机构类型和关系范围。
2. 在隔离候选表中独立搜索现代代理，不读取或复制 CHGIS 坐标。
3. 通过历史来源完成机构身份、驻地和军事关系复核。
4. 冻结候选表，人工复读官方 API 原始坐标和 `precision`。
5. 写入军事单位、地点和关系分片，保留共址地点的稳定 ID。
6. 组装 `data/project.json`，运行结构、时间、来源、关系和坐标校验。
7. 用独立脚本核对批次数量、类型、经纬度范围、来源主张、共址数量和低可信清单。
8. 在军事上下文中复测搜索、点位点击、详情、行政交叉跳转和共址点；行政上下文不得出现大规模军事共址选择菜单。
9. 更新军事批次清单、待复核项、路线图状态和版本记录。
10. 验收通过后才进入 `main` 发布流程；失败批次不得进入正式发布包。

## 8. 批次验收门槛

至少运行：

```text
cargo run -p data-validator -- assemble data/manifest.json
cargo run -p data-validator -- data/manifest.json
cargo test -p data-validator
git diff --check
```

并额外确认：

- 每个首批机构都有稳定 ID、机构类型、1600 年有效性和历史来源；
- 每个可发布点都有 WGS 84 经度、纬度、现代来源和定位方法；
- 原始接口坐标与写入值一致，没有网页显示值、两位小数、平均值或手工偏移；
- 不存在使用 CHGIS 坐标作为军事 `location` 主张的记录；
- 军事隶属、行政所在和共址关系没有互相替代；
- 既有行政单位、地点和共址实体数量没有被意外合并或移动；
- 低可信、区域代理、同名候选和未解析驻地全部进入待复核清单；
- 军事点位使用三角形和省级归属色，行政圆点和军事三角点可以按当前浏览体系分别选择；
- 来源许可、归属、构建资格和发布范围复核通过。

## 9. 回滚与复核

- 发现单个候选错误时，只替换对应军事地点或关系记录，保留审计说明；
- 发现机构身份、时间或军事关系错误时，先撤回该单位及其关系，不批量移动坐标；
- 批次验收失败时，该批不得进入正式发布包，先修复候选表或撤回批次后重新验收；
- 已提交批次使用版本控制回滚，未提交批次保留工作树差异，禁止用不可追踪的覆盖脚本抹掉候选和审计线索；
- 新来源推翻旧候选时，保留旧候选、采用理由和复核日期，不删除历史审计链。

## 10. 与 CHGIS 替换流程的关系

都司定位流程复用 CHGIS 替换流程中的以下操作纪律：

- 先锁定稳定实体，再采集坐标；
- 历史身份链和现代空间链分离；
- 候选独立取得并冻结；
- 原始 API 坐标保真写入；
- 按批次执行结构、来源、坐标、共址和发布资格验收；
- 每次候选更换都保留审计和可回滚记录。

两者的关键差异是：都司定位不是替换既有 CHGIS `location` 主张，不建立 CHGIS 编号迁移清单，也不从 CHGIS 坐标计算偏移或共址。都司还必须额外审查机构类型、军事隶属、行政所在、共址关系和驻地范围，不能只完成一个地点到现代城市的坐标映射。
