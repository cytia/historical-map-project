# 工程规范

## 技术边界

| 层 | 技术与职责 |
|---|---|
| Web UI | React + TypeScript + Vite |
| 地图 | MapLibre GL JS，负责图层、相机和交互 |
| 状态 | Zustand，保存可序列化的应用状态 |
| 首版数据 | JSON / GeoJSON 静态资源 |
| 数据工具 | Rust，负责校验、转换、简化和构建 |
| 后续基础设施 | PMTiles/MVT；确有动态需求后使用 Axum + PostGIS |

不以 Rust/WASM 重写浏览器 UI 或 MapLibre。地图性能优先通过分包、几何简化、按需加载和矢量瓦片改善。

## 地图图层与交互

- 山川地貌是持续可见的基础层；行政疆界以半透明填充和分级边线叠加其上，不用实色遮蔽地形。
- 行政面是主要地图交互目标，支持悬停、选中、层级下钻和详情联动；治所点与标签保持更高的点击优先级。
- 低缩放显示一级区域，中缩放显示府与直隶州，高缩放再显示县级内容，避免同时铺满所有层级。
- 边界可信度必须进入视觉表达；示意或争议边界使用虚线、弱化填充或明确说明。
- 内部交互夹具与正式历史几何分离，必须标明用途和发布资格，不得被正式构建误收录。

行政疆界的图层顺序、缩放层级、点面点击优先级、选中状态和移动端行为统一遵循[行政疆界显示与交互规范](administrative-boundary-display.md)。正式历史面只读取已校验的静态几何，不在浏览器端推算或闭合边界。

## 目录职责

项目建立后遵循以下边界：

```text
src/
  components/     Reusable UI components
  features/       User-facing feature modules
  map/            MapLibre integration and layer definitions
  stores/         Serializable application state
  types/          Shared TypeScript types
  utils/          Pure shared utilities
data/
  sources/        Bibliography and license records
  gazetteer/      Places, names, and administrative units
  periods/        Time-specific spatial data
  physical/       Natural geography layers
tools/            Rust validation and conversion workspace
docs/             Project rules and decisions
```

- `map/` 不拥有业务数据，只把状态转换为地图源、图层和交互。
- `components/` 不直接读写文件或请求外部服务。
- 通用历史类型放在 `types/`，不可在组件中重复定义。
- 大型 GeoJSON 不导入 TypeScript 包，应作为静态资源或瓦片加载。

## 代码规则

- 单个手写源代码文件原则上不超过 200 行；生成文件、类型声明、静态数据和必要配置除外。
- 超过 200 行时应按职责拆分；如拆分会降低内聚性或可读性，须在交付说明中说明保留理由。
- 优先复用项目已有实现。相同或高度相似的逻辑出现两次以上，或已有明确的多个使用场景时，应提取为职责单一的函数、Hook、组件或模块。
- 不为假设中的未来需求提前抽象，不以减少行数为目的制造无意义的文件和转发层。
- TypeScript 开启严格类型检查；不得用 `any` 绕过数据边界。
- 外部 JSON、URL 参数和持久化状态必须在边界处验证。
- React 组件保持展示职责；数据转换放入纯函数或特性模块。
- 地图监听器和资源必须在卸载时释放，避免重复注册。
- Zustand 只保存可序列化业务状态，不保存 MapLibre 实例或 DOM 节点。
- 参数明显增多时使用具名对象，避免依赖位置参数表达复杂语义。
- Rust 公共数据类型使用 `serde`；错误带上下文但不得泄漏敏感值。
- 几何处理必须明确坐标参考系，禁止混用经纬度与平面距离计算。

## 验证要求

按改动范围运行最小充分验证：

- TypeScript：格式检查、静态检查、单元测试和生产构建。
- Rust：格式检查、静态分析和测试。
- 地图 UI：确认加载、缩放、图层切换、点击和移动端基本行为。
- 数据：运行结构、时间、来源、坐标和几何校验。

Bug 必须记录可复现条件，并用测试或明确的复测步骤证明修复。

## 依赖与安全

- 新依赖应解决明确问题；优先使用维护活跃、许可兼容的成熟项目。
- 提交锁文件，避免使用无约束版本或运行时从未知来源加载脚本。
- 新增、升级或重新解析依赖并导致锁文件变化后，必须运行对应生态的依赖安全审计：前端运行 `npm audit`，Rust 运行 `cargo audit`。
- 高危或严重漏洞不得静默忽略；无法立即修复时，交付说明必须记录漏洞、影响范围、缓解措施和暂缓理由。
- 自动修复命令可能改变依赖版本，执行前须确认影响，不得直接使用破坏性升级。
- 外部 HTML 统一净化；外部 URL 限制为允许的协议和来源。
- 密钥使用本地忽略文件或平台 Secrets，不使用前端环境变量隐藏服务端秘密。
- 提交前检查暂存差异中是否包含凭据、私人路径、大型原始文件或许可不明数据。
- 发布前运行依赖审计；高风险漏洞未评估前不得发布。

## Git 与变更范围

- `main` 是唯一长期分支和发布源，必须保持可运行。日常任务默认直接从 `main` 更新、验证和发布，不按会话、版本或地区保留长期分支。
- 只有在 GitHub 分支保护或高风险变更确有需要时，才创建一次性临时分支；合入 `main` 后立即删除远程和本地临时分支。
- 提交应小而完整，描述实际变化，不写工具名称或进度标签。
- 不提交生成缓存、编辑器状态、密钥或无再分发权的原始资料。
- 不修改任务范围外的文件，不将重构混入功能或数据修正。

### GitHub 更新流程

1. 在默认权限上下文中完成只读预检：确认当前目录、`git status -sb`、当前分支、远程分支、远程 tag 和现有 PR。工作区存在无关改动时暂停，不覆盖或代提交。
2. 完成代码或数据修改后，先运行与范围匹配的构建、测试、数据校验和 `git diff --check`。版本号必须显式说明并同步 `package.json` 与 `package-lock.json`，不得静默改版本。
3. 在首次需要写入 `.git` 或访问远程前，一次性申请必要权限；获准后在同一执行上下文完成 `git add`、暂存差异检查、`git commit`、tag 和 push，不在普通沙箱与授权上下文之间反复切换或重试。
4. 直接发布时，先将目标提交推送到 `main`，再创建并推送下一个未占用的注释 tag。受保护的 `main` 使用一次性临时分支和 PR；PR 合入 `main` 后，从更新后的 `main` 创建 tag，再删除临时分支。
5. tag 创建前读取远程 tag。已有 tag 不得强制覆盖；发生 tag 冲突、远程分支拒绝或权限失败时停止并检查远程状态，确认新版本或新权限后再继续。
6. 若目标分支已有 PR，更新该 PR，不重复创建。发布完成后回读 `main`、tag、PR 和工作区状态，确认远程提交与本地预期一致。
7. 只在确认没有未合入的独立提交后关闭过期 PR，并删除对应的远程和本地临时分支；删除前保留必要的 commit 或 tag 引用。

## 决策升级条件

以下变化先更新路线图中的决策，再实施：

- 引入后端、数据库、登录或用户上传。
- 改变历史时间模型、稳定 ID 或公开数据格式。
- 更换地图引擎、瓦片格式或坐标参考系。
- 改变许可证或引入具有传播性条款的数据或代码。
